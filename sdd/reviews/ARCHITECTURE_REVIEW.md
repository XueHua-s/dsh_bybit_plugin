# Independent Architecture Review — Bybit AI Quant

**Date:** 2026-11-17
**Reviewer:** Independent architecture review agent
**Scope:** Current worktree against `AGENTS.md`, SDD Brainstorm/Define/Design, and the installed `software-design-philosophy` skill. This review adds no source or configuration changes. The worktree already contained many unrelated, uncommitted migration changes; observations below describe the state at review time.

## Executive assessment

The repository now has a real, discoverable but still small Nx + pnpm/uv workspace: Nx finds `@bybit-quant/dsh-plugin`, `quant-engine`, and `quant-data`, and its graph contains the `quant-engine → quant-data` edge. This meets the basic project-discovery goal, but the plugin build and unit-test targets currently fail, and the Python root scripts still point to a pre-migration source path. The SDD Verify Gate is therefore not green.

The code is divided into understandable Host, Client, Bybit, state, risk, monitoring, and Python data/runtime modules. The checked handwritten TypeScript and Python files are all under the 500-line cap; `apps/dsh-plugin/src/client.ts` is 494 lines and has little room for feature growth. The Python engine is presently a lifecycle/health skeleton rather than a long-running quant data plane. WebSocket ingestion and reconnect monitoring are not configured. No reviewed evidence proves official DSH Plugin Manager install, upgrade, or uninstall behavior; no claim about the installed Harness or current Bybit account state is made here.

**Design-philosophy score: 6/10 (5 of 8 diagnostic rows pass).** Passes: module boundaries are mostly describable, transport/config details are partly hidden, important boundaries have intent comments, design discussion exists in SDD, and newcomers can locate the main project boundaries. Not yet demonstrated: interfaces are consistently simpler than implementations, implementation changes stay local across all boundaries, or reviews routinely measure structural improvement. To reach 10/10, first fix the runnable build/test boundary and root scripts, keep host lifecycle teardown explicit, split the near-limit client by cohesive knowledge, and record design checks with evidence as capabilities are implemented.

## Positive evidence

- `pnpm exec nx show projects --json` returned three independently named projects: `quant-data`, `quant-engine`, and `@bybit-quant/dsh-plugin`.
- Nx graph output records `quant-engine → quant-data`; the plugin has no shared TS package dependency, consistent with the current absence of a justified `packages/ts/*` package.
- `pnpm-workspace.yaml` discovers `apps/*` and `packages/ts/*`; `python/pyproject.toml` defines a uv workspace over `packages/*` and `apps/*`.
- Handwritten source is TypeScript for the plugin and Python for the Python workspace. Current package TS config enables strict mode; no `any` escape was observed in inspected production source.
- All inspected handwritten TS/Python files are below 500 lines. The scan excluded `python/.venv` and generated `dist` output.
- `apps/dsh-plugin/src/host-runtime.ts` resolves credential names through the Host credential service and registers the runtime monitor with `ctx.effect`, whose return value is the monitor stop callback. This is lifecycle ownership evidence; it does not prove external unload behavior.
- `apps/dsh-plugin/cordis.patch.yml` defaults to Testnet, keeps `allowLiveTrading: false` and `allowMainAccount: false`, and contains credential names rather than values. `host-config.ts` only accepts explicit `true` for live/Testnet/main-account switches.
- `apps/dsh-plugin/src/lib/trust.ts` documents untrusted external text. `sandbox.ts` uses a network-disabled, read-only container with dropped capabilities and resource limits, although the host-side output accumulation gap remains.
